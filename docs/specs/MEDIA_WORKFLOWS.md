# قرارداد اصلی محصول: فیلم‌ها، پوشه‌ها، SSD و هارد

این سند نیازمندی اجرایی Cutora است، نه ادعای قابلیت موجود. نسبت به MVP اولیه، مدیریت هارد و انتقال رفت‌وبرگشت صریح‌تر و جزو هسته شده است. تا پاس‌شدن آزمون‌های انتهای سند، عبارت «مدیریت رسانه آماده است» درست نیست.

## نتیجه‌ای که کاربر باید ببیند

کاربر در یک کتابخانه بفهمد چه فیلمی دارد، موضوع و رویداد آن چیست، نسخه اصل کجاست، کدام هارد باید وصل شود، چه چیزی بکاپ دارد و برای تدوین چه کاری لازم است. برنامه بقیه مسیرها، manifest، queue، نام‌گذاری و بررسی صحت را مدیریت کند. کاربر نباید hash یا source ID را برای عملیات معمول بفهمد.

چهار اقدام اصلی به زبان ساده:

| اقدام | تجربه کاربر | رفتار واقعی |
|---|---|---|
| «واردکردن فیلم‌ها» | منبع → نام رویداد پیشنهادی → شروع | کپی امن به Library، تأیید، index و بکاپ در صورت اتصال |
| «برای تدوین آماده کن» | انتخاب چند کلیپ یا رویداد → انتخاب SSD | ساخت/استفاده مجدد working copy محلی از همان Asset؛ اصل هارد حفظ می‌شود |
| «روی هارد آرشیو کن» | انتخاب رویداد → هارد مقصد → دیدن نتیجه | کپی تأییدشده به آرشیو؛ گزینه آزادکردن نسخه محلی جدا و مشروط |
| «بازیابی کن» | انتخاب رسانه/پروژه/بکاپ → مقصد | بازگردانی به مسیر تازه، بررسی hash، relink؛ نه overwrite بی‌اجازه |

«افزودن پوشه موجود به کتابخانه» و «پیداکردن دیسک/مسیر» اقدام کمکی کنار همین‌هاست. اجرای عملیات روی چندصد فایل در یک job ممکن باشد؛ انتخاب تک‌تک فایل‌ها لازم نباشد.

## ۱. مفهوم Asset و نسخه‌ها

- **Asset:** محتوای یکتای یک فایل اصلی؛ hash کامل، metadata و شناسه پایدار دارد. مسیر فایل، شناسه Asset نیست.
- **Occurrence:** اینکه همین محتوا با چه نام، منبع و نشست ضبط/ورود دیده شده است. فایل‌های بایتی یکسان می‌توانند سابقه‌های مختلف داشته باشند.
- **Replica:** نسخه فیزیکی روی SSD، هارد یا دیسک بکاپ، با نقش، storage identity، مسیر، وضعیت و زمان آخرین بررسی.
- **Derivative:** thumbnail، proxy، waveform و render؛ با اصل اشتباه نشود و قابلیت بازتولید مشخص باشد.
- **Collection/Event:** گروه منطقی برای رویداد/پروژه؛ عضویت چندگانه، نه الزام به چند کپی خام.

وجود همان Asset روی SSD و هارد می‌تواند کاملاً عمدی باشد. آن را «duplicate اضافی قابل حذف» معرفی نکنیم. dedupe مانع import خام اضافه می‌شود، اما replica لازم برای تدوین یا بکاپ را حذف نمی‌کند. SHA-256 تصویر مشابه یا فایل دوباره encodeشده یکی نیست؛ تشابه بصری فقط پیشنهاد گروه‌بندی است.

## ۲. تنظیم یک‌باره، نه wizard در هر بار

کاربر Library اصلی، فضای کاری SSD، مقصد بکاپ و در صورت نیاز مقصد آرشیو HDD را تعیین کند. این نقش‌ها می‌توانند در ابتدا کمتر باشند؛ جدا بودن فیزیکی storage برای ادعای بکاپ بررسی شود. دو مسیر یا partition روی یک دیسک، بکاپ مستقل نیستند.

برنامه نام دوستانه دیسک و هویت پایدار آن را ثبت کند، نه فقط `E:`. تغییر حرف درایو، دستگاه را گم نکند. تشخیص هویت اگر قطعی نیست، نام/ظرفیت را به‌عنوان شواهد کمکی نشان بده و برای relink تأیید بگیر؛ به اولین USB با همان حرف اعتماد نکن.

برای استفاده روزانه تنظیمات مقصد و قانون دسته‌بندی یادآوری شود. نام رویداد از کاربر یا preset قابل انتخاب؛ تنظیمات پیشرفته در پنل ثانویه. انتخاب filesystem source همیشه fallback داشته باشد. هیچ برنامه‌ای فقط با واردکردن مسیر فرضی توسعه‌دهنده کار نکند.

## ۳. واردکردن از GoPro، کارت و پوشه

**وضعیت‌ها:** شناسایی → اسکن فایل‌ها → آماده/نیازمند اقدام → کپی → بررسی صحت → بکاپ/در انتظار بکاپ → تکمیل/تکمیل با خطا.

پیش‌نمایش ورود فقط چند داده مهم: تعداد/حجم جدید، تکراری قطعی/نیازمند بررسی، تعداد فایل نامعلوم/مشکل‌دار، مسیر مقصد، وضعیت هارد و فضای موردنیاز. اصل‌های جدید پیش‌فرض انتخاب باشند. فایل‌های خراب یا ناشناخته بی‌صدا نادیده گرفته نشوند.

source read-only، مقایسه اندازه/زمان پیش و پس از خواندن، کپی به temporary در همان مقصد، hash هنگام خواندن، flush و readback مقصد، سپس rename امن و ثبت catalog. «بایت‌ها درست منتقل شدند» از «ویدئو قابل decode است» جدا ثبت شود. فایل خراب source می‌تواند دقیق کپی شود؛ ظاهر سبز مبهم ندهیم.

اگر کارت یا دوربین جدا شد، job متوقف/منتظر منبع شود، فایل‌های کامل معتبر باقی بمانند و source مجدد شناسایی شود. ادامه در سطح فایل/نشست کافی است؛ ادامه بایتی MTP تا اثبات seek و هویت source قول داده نشود. تغییرات بین اسکن و کپی دوباره ارزیابی شوند.

file discovery: MP4/JPG و companionهای LRV/THM، و سایر انواع واقعی دوربین در صورت وجود. import کامل همراه‌ها را حفظ کند؛ gallery پیش‌فرض اصل‌ها را نشان دهد تا هر ضبط سه بار دیده نشود. رابطه همراه‌ها بر حسب دستگاه/الگوی معتبر تشخیص داده شود؛ فایل کم‌کیفیت هرگز جای اصل 4K را نگیرد.

برای MTP، adapter واقعی WPD جدا از filesystem است. در USB از drive letter ساختگی یا polling موفقیت بر اساس سایز نهایی تنها استفاده نکن. timeout/خطای دستگاه با تعداد/فهرست نتیجه ثبت شود. روش دوربین آزمایش‌شده و روش کارت‌خوان هرکدام badge پشتیبانی خودش را داشته باشد.

## ۴. پوشه‌بندی قابل فهم و پایدار

ساختار پیش‌فرض پیشنهادی برای Library تحت مدیریت، قابل انتخاب در setup:

```text
CutoraLibrary/
  library.json
  catalog/
  originals/
    2026/10/2026-10-29_<session-id>/
      GX010001.MP4
      GL010001.LRV
      GX010001.THM
  manifests/<session-id>.json
  collections/<collection-id>.json
  projects/<project-id>/
    selection.json
    handoff/
  ready/<project-id>/
  cache/
    thumbnails/
    proxies/
```

شناسه session از برخورد نام یکسان جلوگیری کند؛ نام اصلی برای سازگاری دوربین/پروژه حفظ شود. نام و عنوان فارسی رویداد در metadata نمایش داده شود. اگر کاربر نام رویداد را عوض کرد، مسیر اصل خودکار جابه‌جا نشود. مرتب‌بودن به معنی تغییر مداوم اسم فایل و شکستن link پروژه DaVinci نیست.

در صورت انتخاب نام پروژه در پوشه، sanitization نام‌های رزروشده Windows، طول مسیر، نقطه/فاصله انتهایی، Unicode و collision لازم است. معنای نام واردشده در catalog حفظ شود. مسیرهای نمایش‌داده‌شده قابل بازکردن در Explorer باشند؛ «کپی مسیر» هم در منوی جزئیات باشد.

رویداد/موضوع در کتابخانه مجازی است: یک فیلم می‌تواند هم بازسازی، هم ASMR و هم اپیزود اول باشد، بدون سه کپی خام. export یک مجموعه به پوشه اشتراکی، یک عملیات صریح جداست؛ labelزدن چنین exportی انجام نمی‌دهد.

## ۵. دسته‌بندی که واقعاً کار را کم کند

### پایه بدون مدل یا API

- تاریخ ضبط با اولویت metadata معتبر؛ تاریخ filesystem fallback با برچسب «تخمینی». ساعت/منطقه زمانی دوربین نامشخص را جعل نکن.
- گروه ورود/روز و پیشنهاد event براساس فاصله زمانی قابل تنظیم. این پیشنهاد است، نه تشخیص قطعی اتفاق واقعی.
- نوع رسانه، مدت، اندازه، codec، resolution، orientation، وجود صدا و chapterهای احتمالی.
- موضوع‌های اولیه قابل انتخاب: بازسازی خانه، ولاگ دونفره، موتورسواری، ASMR، آشپزی و روزمره؛ اضافه/حذف/نام‌گذاری مجدد توسط کاربر.
- favorite، امتیاز ساده، یادداشت و نشان «برای تدوین انتخاب شد».
- فیلتر ترکیبی تاریخ/موضوع/رویداد/دیسک/بکاپ/مدت/آماده تدوین، بدون جابه‌جایی صفحه زیاد.

### کمک هوشمند مرحله بعد

speech transcription برای جست‌وجو، scene/keyframe برای مرور و پیشنهاد topic/رویداد با اطمینان. نتیجه مدل manual override را بازنویسی نکند. merge/split/undo دسته‌ها آسان باشد. auto-tag به معنی انتقال فیزیکی یا حذف ویدئو نیست. بدون AI، کل مسیر پایه باید مفید باشد.

## ۶. افزودن آرشیو قدیمی روی هارد

هنگام انتخاب پوشه قدیمی، دو انتخاب روشن:

۱. **«فقط به کتابخانه اضافه کن»**: metadata و fingerprint/index لازم، فایل‌ها در همان هارد می‌مانند، هیچ rename یا بازچینی پیش‌فرض انجام نمی‌شود. محل فعلی به عنوان replica/منبع خارجی ثبت شود. بررسی کامل hash می‌تواند job پس‌زمینه باشد؛ تا پایان، dedupe قطعی یا verified بودن ادعا نشود.

۲. **«به آرشیو Cutora کپی و مرتب کن»**: preview مسیر و حجم، کپی verified به ساختار managed، source قبلی حفظ شود. حذف پوشه قبلی خارج این عملیات است.

اسکن recursive باید چرخه junction/symlink، system/recycle folders و مقصدی که زیر source افتاده را کنترل کند. همه دیسک کاربر را بی‌اجازه اسکن نکن. ignoreها قابل مشاهده و scan report با تعداد موفق/خطا موجود باشد. خارج‌کردن پوشه از catalog هم با حذف فایل تفاوت دارد و پیش‌فرض فقط رابطه را حذف کند.

اگر هارد قطع است، thumbnail و metadata آخرین مشاهده در کتابخانه بماند؛ روی آن «روی هارد X؛ متصل نیست» دیده شود. تعداد نتایج جست‌وجو رسانه offline را پنهان نکند مگر کاربر فیلتر بزند. preview غیرقابل دسترس پیام صحیح بدهد، نه thumbnail سیاهِ بی‌توضیح.

## ۷. از هارد به SSD: برای تدوین آماده کن

کاربر یک event/پروژه یا چند کلیپ را انتخاب و فقط «برای تدوین آماده کن» بزند. برنامه مقصد SSD قبلی، حجم موردنیاز و وجود working copy سالم را بررسی کند؛ نسخه سالم موجود را دوباره کپی نکند. منبع مناسب از replica موجود/آنلاین و معتبر انتخاب شود، بدون حذف نسخه هارد.

working copy با همان Asset ID و نقش `working` ثبت شود؛ صفحه کتابخانه شلوغ و duplicate نشود. پروژه/انتخاب‌ها به مسیر پایدار workspace ارجاع دهند؛ جابه‌جایی cache نباید reference اصل را عوض کند. اگر original روی هارد است و فقط proxy محلی داریم، UI فرق را نشان دهد؛ «قابل preview» به معنی «قابل render کیفیت اصلی» نیست.

در حالت کمبود فضا، گزینه انتخاب فایل کمتر، proxy موقت یا تغییر SSD بده؛ اصل را برای جا بازکردن خودکار پاک نکن. ساخت proxy به permission مستقل نیاز ندارد اگر روی فضای managed مجاز انجام می‌شود، ولی حجم و job قابل لغو باشد.

پس از تدوین، «پاکسازی فضای کاری» تنها مشتق‌ها و working copyهایی را پیشنهاد دهد که نسخه retained لازم آنلاین/verify شده است و reference پروژه نیاز به مدیریت ندارد. فایل خروجی تنها نسخه یا اصلِ بدون replica، cache محسوب نشود.

## ۸. از SSD به هارد: آرشیو و جابه‌جایی واقعی

پیش‌فرض «کپی تأییدشده روی هارد» است: source حفظ، destination verified و replica ثبت شود. خام، manifest و metadata/selection مرتبط در بسته آرشیو قرار بگیرند؛ proxy اختیاری و قابل بازتولید باشد. مقصد موجود merge کور یا overwrite نگیرد؛ collision plan پیش از نوشتن نمایش داده شود.

کاربر ممکن است بخواهد بعد از آرشیو، SSD آزاد شود. UI باید دو مرحله متمایز داشته باشد:

۱. **آرشیو و تأیید**؛ بدون حذف.
۲. **آزادسازی نسخه محلی انتخاب‌شده**؛ نمایش دقیق فایل‌ها/حجم و تأیید صریح همین مجموعه. در مورد original، مقصد تأییدشده و نسخه retained مستقل موردنیاز پس از حذف باید باقی بمانند؛ یک نسخه نهایی تنها، بکاپ محسوب نمی‌شود.

نبود replica کافی مانع کپی امن نشود؛ فقط cleanup تخریبی را غیرفعال کند و دلیل کوتاه بدهد. گرفتن اجازه کلی «پروژه را بساز» یا انتخاب label «آرشیو» به معنی رضایت حذف نیست. ادغام دو مرحله در دکمه مبهم «Move» ممنوع است.

جابجایی Library root هم job جداست: snapshot سازگار catalog/manifest، copy/verify، preview محل جدید و relink، تست چند اصل و پروژه، سپس activation مقصد. DB باز یا WAL نیمه‌کپی‌شده با کپی صرف `.db` جابه‌جا نشود. root قدیمی تا اجازه جداگانه حفظ شود. rename اتمیک بین دو volume وجود ندارد؛ copy+verify+switch+cleanup طراحی شود.

## ۹. بکاپ، دسترسی آفلاین و بازیابی

وضعیت integrity و availability جدا باشند. Replica می‌تواند آخرین بار verified شده ولی اکنون offline باشد. dashboard باید مثلاً «بکاپ تأییدشده؛ هارد الان متصل نیست» نشان دهد، نه «الان تأیید شد».

بکاپ file copy مستقل با readback و ثبت زمان است؛ دو پوشه روی یک دیسک آن را برآورده نمی‌کنند. اتصال دوباره هارد باید فقط pendingها/تغییرات لازم را صف کند. job بکاپ شکست‌خورده، موفقیت import را از بین نبرد؛ نتیجه نهایی تفکیک‌شده باشد.

بازیابی از بکاپ به مسیر تازه پیش‌فرض است؛ انتخاب نسخه/تاریخ و مقایسه manifest، بررسی فضای مقصد، copy/verify و سپس ثبت replica. فایل مقصد متفاوت خودکار overwrite نشود. `restore preview` تعداد قابل دسترس، مفقود، conflict و حجم را نشان دهد. بازیابی catalog و media هر دو آزمون شوند.

بردن کتابخانه از لپ‌تاپ به کیس: metadata و manifest بدون secrets، مسیرهای نسبی و storage identity export/import شوند. کاربر root جدید را معرفی کند؛ original از روی hash/identity match شود و metadata/selection حفظ شود. tokenها و تنظیمات شخصی DPAPI قابل کپی بین کاربران فرض نشوند. واردکردن دوباره بسته، رویدادها را بی‌دلیل تکثیر نکند.

## ۱۰. ارتباط با پروژه DaVinci

قبل از تحویل، انتخاب‌ها و اصل/working copy موردنیاز آنلاین باشند. handoff شامل فهرست مسیرهای قطعی، زمان/ترتیب انتخاب و فایل subtitle در صورت وجود است. بازکردن DaVinci یا export XML به‌تنهایی اثبات import موفق نیست؛ مسیر دستی قابل اتکا هم ارائه شود.

جابجایی آرشیو می‌تواند پروژه خارجی را offline کند. Cutora مسیر قدیم/جدید و عملیات نیازمند relink را نمایش دهد؛ تغییر مخفی در database اختصاصی DaVinci انجام ندهد. در صورت API مجاز و تست‌شده، relink روی project copy و با checkpoint انجام شود. در غیر این صورت، پوشه پایدار handoff و دستور کوتاه relink ارائه شود.

بدون اثبات round-trip، subtitle، Fusion، افکت یا speed ramp از XML/EDL حفظ‌شده فرض نشوند. ادیت اصلی داخل Resolve و قالب/agent آینده شرط صحت مدیریت فایل نیستند.

## ۱۱. صف، خطا و ظرفیت

هر کار یک job با plan ثابت/revision، source/destination identity، شمار فایل و بایت، مرحله، retry و نتیجه دارد. قبل شروع دوباره فضای هر مقصد و هویت source کنترل شود. queue محدود؛ انتقال/verify اولویت بالاتر از thumbnail و AI دارد. hash/DB روی thread UI نباشند.

لغو: source سالم، فایل‌های commitشده معتبر، partial مشخص، امکان ادامه. crash بعد rename و قبل DB commit یا عکس آن در شروع reconcile شود. اسم destination موجود مجوز موفقیت نیست. job پس از restart با version schema معتبر بازیابی شود.

فضا: اصل‌های جدید + temporary همان عملیات + مشتق‌ها/خروجی لازم + حاشیه رزرو، به تفکیک volume. peak موقت readback یا relocation لحاظ شود. پرشدن دیسک حین نوشتن، نتیجه verified ندهد. cache سقف دارد و cleanup آن باید به resolved managed path محدود باشد؛ raw/ready تنها نسخه هرگز هدف cache cleanup نیست.

کامپیوتر خوابیده/خاموش، انتقال را اجرا نمی‌کند. بعد روشن‌شدن وضعیت قبلی بازیابی و به source موجود وابسته شود. auto-start/tray انتخابی است؛ startup service پنهان و admin اجباری نساز. روی هارد کند زمان واقعی و progress قابل فهم مهم‌تر از animation ظاهراً سریع است.

## ۱۲. حالت‌های UI و اصطلاحات

در صفحه جزئیات هر رسانه، سه پرسش پاسخ داده شود: «کجاست؟»، «سالم بررسی شده؟»، «بکاپ مستقل دارد؟». اطلاعات فنی در disclosure، نه صفحه اصلی.

| وضعیت | نمایش درست |
|---|---|
| source شناسایی شد | فقط اتصال/هویت؛ هنوز کپی نشده |
| در حال ورود | مرحله، شمار فایل و بایت واقعی |
| کپی تأیید شد | integrity همان replica، نه ادعای بکاپ |
| بکاپ در انتظار | دلیل/هارد موردنیاز و اقدام اتصال |
| بکاپ تأیید شد | مقصد مستقل و تاریخ آخرین verify |
| آفلاین | metadata هست، دیسک برای دسترسی اصل باید وصل شود |
| نیاز به بررسی | داده نامطمئن/خطا/تغییر source؛ اقدام روشن |
| آماده تدوین | فایل موردنیاز واقعاً آنلاین، نه صرف thumbnail |

هر جریان یک primary CTA و پیش‌فرض امن داشته باشد. summary پایان: جدید/تکراری/خطادار، محل ذخیره، وضعیت بکاپ و کارهای معوق. نبود اینترنت، ASR، Studio یا account اجتماعی نباید این چهار workflow اصلی را از کار بیندازد.

## ۱۳. معیارهای پذیرش الزام‌آور

همه معیارها اکنون **Not Run** هستند؛ توسعه‌دهنده بعدی در STATUS شاهد Pass/Fail بنویسد. نمونه‌ها fixture باشند و داده واقعی فقط با اجازه خواندن/کپی تست شود.

| ID | آزمون | نتیجه لازم |
|---|---|---|
| MW-01 | import همان ۲۰ فایل سه بار | یک Asset برای محتوای یکسان، occurrence صحیح، بدون کپی خام اضافی |
| MW-02 | نام و اندازه یکسان، بایت متفاوت | هر دو محتوا حفظ؛ overwrite/حذف نشود |
| MW-03 | قطع/kill در copy، verify، rename و commit | source ثابت؛ recovery بدون ثبت verified کاذب |
| MW-04 | بکاپ غایب و اتصال بعدی | import صحیح با pending؛ پس از اتصال فقط لازم‌ها copy/verify شوند |
| MW-05 | دو مسیر/partition روی یک دیسک | ادعای بکاپ مستقل رد یا با دلیل نیازمند انتخاب مقصد شود |
| MW-06 | index آرشیو قدیمی، حالت فقط افزودن | metadata قابل جست‌وجو؛ hash/original name/path محتوا تغییر نکند |
| MW-07 | HDD → working SSD، دوبار همان انتخاب | اصل حفظ؛ بار دوم reuse نسخه سالم؛ یک رسانه در library |
| MW-08 | SSD → archive HDD، سپس درخواست cleanup | ابتدا copy verified؛ cleanup بدون مجوز/replica کافی ممنوع |
| MW-09 | قطع هارد و تغییر حرف درایو | thumbnail باقی؛ offline صحیح؛ relink هویت، نه اعتماد کور به letter |
| MW-10 | restore اصل و catalog به مسیر تازه | hash برابر، tag/event/selection حفظ، conflict بدون overwrite |
| MW-11 | انتقال package کتابخانه به سیستم/مسیر تازه | root قابل معرفی، metadata سالم، اسرار منتقل نشوند، import مجدد idempotent |
| MW-12 | تغییر نام/merge/split موضوع و رویداد | اصلاح و undo؛ اصل جابه‌جا یا تکثیر نشود |
| MW-13 | LRV/THM و chapterها | همراه حفظ ولی gallery سه برابر نشود؛ اصل خروجی همان کیفیت اصلی |
| MW-14 | کمبود فضا، read-only و فایل >۴GiB | preflight/خطای درست؛ هیچ فایل نیمه‌کاره verified نشود |
| MW-15 | مسیر فارسی، long path و junction مقصد بیرون | مسیر معتبر کار کند؛ cleanup/recurse از دامنه مجاز خارج نشود |
| MW-16 | handoff و جابه‌جایی path در پروژه آزمایشی Resolve | media offline آشکار؛ mapping/relink واقعی یا راهکار دستی روشن |
| MW-17 | CPU-only/بدون cloud/بدون Resolve | مدیریت هسته کار کند؛ قابلیت وابسته واضح غیرفعال شود |
| MW-18 | فیلم خراب ولی بایت‌های copy برابر | integrity و media-health جدا؛ warning decode حفظ شود |
| MW-19 | queue همراه جست‌وجو/scroll کتابخانه | UI responsive، لغو و pause معنی‌دار، progress واقعی |
| MW-20 | consent و revision job | تغییر source/مقصد بعد تأیید plan دوباره بررسی شود؛ رضایت قدیمی روی فایل تازه اعمال نشود |

نمونه واقعی اثبات‌شده و گزارش تست، شرط نهایی اعتماد است. نوشتن این مشخصات یا ساخت UI زیبا به معنی پاس‌شدن این معیارها نیست.
