# ورود، ذخیره‌سازی، بکاپ و پردازش رسانه

این سند قرارداد طراحی است؛ پیاده‌سازی جدید یا آزمون خطای واقعی در این مرحله انجام نشده است.

## منبع و اتصال

کارت‌خوان SD مسیر اصلی پیشنهادی است: فایل‌سیستم معمولی، ابزارهای استاندارد، خواندن قابل کنترل و خطای قابل مشاهده. برای تولیدکننده‌ای که مرتب ضبط می‌کند، یک حرکت فیزیکی اضافه می‌تواند هزینه نگهداری adapter ناپایدار را کاهش دهد. برای اتصال مستقیم USB، از رابط WPD/MTP ویندوز استفاده شود؛ حافظه را به زور به drive letter تبدیل نکنیم. [عملیات رسمی WPD](https://learn.microsoft.com/en-us/windows/win32/wpd_sdk/operating-on-device-content)

در انتقال قبلی این نشست، HERO10 از طریق MTP خوانده شد؛ CopyHere و readback کار کردند، ولی resolve کردن مسیر Shell برای حذف خطا داد و روش مبتنی بر شناسه شیء لازم شد. این یک مشاهده موردی است، نه آزمون دوام importer. راهکار تولیدی را بر CopyHere تعاملی با progress مبهم و timeout حدسی بنا نکنیم. پشتیبانی USB تا آزمون WPD در P1 باقی بماند.

Auto Detect بدون برنامه در حال اجرا کار نمی‌کند. اجرای tray و شروع با Windows اختیاری است. منبع جدید باید یک بار توسط کاربر مجاز شود؛ هر دیسک USB به‌طور خودکار منبع فیلم خانوادگی نیست. برای منبع شبکه یا پوشه ابری on-demand، P0 قول صحت همانند فایل محلی ندهیم.

## قرارداد ورود ایمن

۱. فهرست اولیه فایل‌ها، source identity، نام، سایز و زمان ثبت شود. فایل هنوز در حال ضبط یا تغییر با snapshot ثابت اشتباه نشود؛ دوربین هنگام انتقال ضبط نکند.

۲. ظرفیت مقصد و بکاپ مستقل، permission، فایل‌سیستم و سقف فایل بررسی شود؛ FAT32 برای فایل بیش از ۴GiB مناسب نیست. فضای رزرو باید از روی نیاز job تعیین شود، نه فقط یک درصد ثابت.

۳. فایل به نام موقت یکتا در همان volume مقصد نوشته شود؛ در زمان خواندن source، SHA-256 محاسبه شود. ورودی read-only است. طول و وضعیت source در پایان دوباره کنترل شود.

۴. flush و بستن handle، خواندن دوباره مقصد و مقایسه hash و اندازه. «درستی بایت» و «سلامت محتوای قابل decode» دو نتیجه جدا باشند؛ فایل خراب روی کارت می‌تواند کاملاً درست کپی شود.

۵. rename در همان filesystem و commit کوتاه ثبت Asset/SourceOccurrence. تراکنش DB و rename یک تراکنش اتمیک مشترک نیستند؛ journal باید هر دو حالت «فایل هست/DB نیست» و «رکورد هست/فایل نیست» را در شروع برنامه reconcile کند. فایل موجود هرگز با نام همسان overwrite نشود.

۶. کار بعدی فقط پس از ثبت صحت آن فایل شروع شود. در قطع اتصال، فایل کامل قبلی حفظ و incomplete مشخص باشد. resume پیش‌فرض در سطح فایل/نشست است؛ ادامه بایتی فایل نیمه‌کاره فقط با source ثابت و seek معتبر بعداً اضافه شود.

۷. dedupe کامل با hash کل فایل انجام شود. اندازه و quick hash فقط پیش‌فیلترند. نام تکراری/تاریخ یکسان مجوز حذف نیست. اگر بایت یکسان است، SourceOccurrence تازه ثبت و به Asset قبلی متصل شود؛ backup status آن Asset همچنان باید بررسی شود.

## اصل، فایل کمکی و شناسه

MP4/JPG و در صورت وجود GPR/WAV خام حفظ شوند؛ فرمت ناشناخته هشدار بگیرد و بی‌صدا نادیده گرفته نشود. LRV و THM همراه همان نشست نگه‌داری شوند؛ برای نمایش مشتق مفیدند، اما جایگزین اصل نیستند. در صورت نام‌گذاری متفاوت LRV/MP4، رابطه را فقط بر تشابه نام قطعی نکنیم. [توضیح GoPro](https://community.gopro.com/s/article/What-are-thm-and-lrv-files?language=en_US)

فایل‌های chapter یک ضبط ممکن است چند MP4 باشند. کتابخانه می‌تواند گروه ضبط پیشنهاد بدهد، ولی بایت‌ها و نام اصلی حفظ شوند؛ ادغام خودکار خام در P0 انجام نشود. timezone زمان ضبط اگر نامشخص است «نامشخص» ثبت شود؛ UTC از روی حدس تولید نکنیم. تاریخ نادرست دوربین امکان اصلاح metadata در catalog داشته باشد، بدون دست‌کاری فایل خام.

ساختار پیشنهادی کتابخانه، صرفاً برای طراحی:

```text
Library/
  originals/YYYY-MM-DD/session-id/original-filename
  manifests/session-id.json
  projects/project-id/selection.json
  ready/project-id/
  cache/thumbnails/
  cache/proxies/
  catalog/
```

شناسه Asset مستقل از مسیر است. تغییر drive letter با volume identity و relink حل شود. Windows reparse point، symlink و مسیر بیرون Library در job پاکسازی cache بررسی شوند. لینک سخت، دو پوشه روی یک دیسک و دو پارتیشن یک دیسک، بکاپ مستقل نیستند.

## بکاپ

دو SSD داخلی در دو دیسک فیزیکی در برابر خرابی یکی کمک می‌کنند، اما در برابر سرقت، بدافزار و آسیب مشترک کیس کافی نیستند. توصیه مقصد: اصل روی SSD، replica تأییدشده روی هارد مستقل، و در ادامه نسخه سوم جدا از دستگاه/مکان با روش مورد تأیید کاربر. خرید یا cloud فعلاً اجرا نشود.

Replica states: `pending → copying → verifying → verified` و `missing/stale/error`. جداشدن هارد، داده تاریخی verified_at را پاک نمی‌کند، ولی availability را offline می‌کند؛ UI نباید آن را بکاپ آنلاین فعلی نشان دهد. حجم ثبت‌شده به تنهایی نتیجه موفقیت نیست.

از original به مقصد دوم copy، flush و readback hash انجام شود. سپس هر جلسه حداقل یک restore واقعی به مسیر تازه و checksum؛ برای حذف کارت در آینده همه فایل‌های منتخب باید دو نسخه مستقل تأییدشده داشته باشند. نسخه بدون بکاپ مانع تولید محتوا نیست، اما مجوز حذف اصل نمی‌دهد.

حذف دوربین در محصول P0 اصلاً قابلیت ندارد. در آینده فقط درخواست جداگانه، نمایش تعداد/حجم، شناسایی مجدد source و تأیید صریح همان مجموعه؛ AI و job پس‌زمینه مجوز حذف ندارند. پاکسازی فقط cache قابل بازتولید و پوشه‌های allowlist شده را هدف بگیرد.

DB را با SQLite backup API یا snapshot سازگار و WAL checkpoint کنترل‌شده ذخیره کنید؛ کپی بی‌هماهنگ تنها فایل `.db` در زمان نوشتن، backup معتبر نیست. Catalog باید از manifestها قابل بازسازی باشد؛ restoration خود catalog هم آزمون شود.

## ظرفیت و هزینه فضا

برای bitrate فرضی ۱۰۰Mbps: `۱۰۰ × ۳۶۰۰ ÷ ۸ = ۴۵GB` در ساعت، قبل از صوت/سربار. برای ۱۲۰Mbps حدود ۵۴GB/h. این‌ها محاسبه‌اند، نه bitrate اندازه‌گیری‌شده فایل‌های کاربر. یک هارد با ۵۰۰GB فضای واقعاً آزاد، قبل از حاشیه ایمنی فقط حدود ۹–۱۱ ساعت از چنین خامی نگه می‌دارد.

ظرفیت موردنیاز هر volume = اصل‌های تازه + temporary همان job + cache مجاز + خروجی‌های برنامه‌ریزی‌شده + حاشیه رزرو. replica روی volume خودش جدا محاسبه شود. اگر temp پس از rename به original تبدیل می‌شود، هر دو را بی‌دلیل دو بار در ظرفیت دائم نشماریم؛ readback مستقل MTP می‌تواند فضای موقت اضافه بخواهد.

روی سیستم فعلی فضای C بسیار کم است؛ build، مدل و cache نباید بدون بررسی آنجا دانلود شوند. روی سیستم هدف، فضای خالی سه دیسک هنوز اندازه‌گیری نشده. فایل‌های فعلی ۹٫۶GB یک نسخه شناخته‌شده دارند؛ اقدام پیشنهادی اول برای آن‌ها بکاپ مستقل است، ولی این مأموریت فقط مستندسازی است.

## pipeline پردازش

`original verified → ffprobe JSON → poster frame → optional proxy → preview/selection → DaVinci → ready output → ffprobe + decode/visual QC`

- FFprobe مدت، codec، ابعاد، نرخ فریم به صورت کسر، audio و rotation را ثبت کند. فایل بدون audio، VFR، slow-motion و timelapse جدا شناسایی شوند.
- thumbnail در زمان مفید پیشنهاد شود؛ فریم اول سیاه تنها تصویر کتابخانه نباشد. تولید روی صف کم‌اولویت پس از ورود حیاتی.
- proxy با H.264/AAC و resolution پایین‌تر، mapping به اصل و timebase معتبر. GPU موجود ممکن است decode یا encode را پشتیبانی کند؛ هر دو جدا تشخیص داده شوند. CPU fallback و رقابت GPU با Resolve/ASR مدیریت شود.
- concurrency پیشنهادی: یک انتقال منبع، یک کار سنگین GPU، تعداد کمی thumbnail CPU. این مقدار پیش‌فرض آزمون‌پذیر است، نه بهینه قطعی.
- crop، scale، pad، trim، concat، resample و صف batch با FFmpeg ممکن‌اند؛ اما تبدیل نسبت با انتخاب مرکز ثابت، auto-reframe معنایی نیست. کادر برای هر شات بازبینی شود؛ برای دو نفر/موتور/ابزار، center crop ممکن است محتوای مهم را حذف کند.
- preset خروجی پیشنهادی MP4 H.264/AAC، 1080×1920، 1080×1350، 1920×1080. نرخ فریم پروژه صریح انتخاب شود و خروجی صوت sync بماند. فیلتر یا burn-in نیازمند encode مجدد است؛ lossless trim در نقطه دلخواه تضمین نشود.
- stream GPMF/GPS خام حفظ شود؛ در خروجی عمومی، فقط streamهای تصویر/صوت موردنیاز map شوند. اطلاعات مکان/مسیر خانه بی‌قصد منتشر نشود.

در P0 DaVinci موتور تدوین و خروجی اصلی است. FFmpeg برای ورود/preview/QC استفاده می‌شود؛ ساخت pipeline رندر دوم تا نیاز واقعی P1 به تعویق بیفتد. برای ASMR نویزگیری، حذف سکوت، compressor و موسیقی خودکار پیش‌فرض خاموش است.
